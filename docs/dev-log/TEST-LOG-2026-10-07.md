- **现象**：点「烧录」（欢迎页示例 welcome.ino → COM29），37.5s 后任务失败：`Compiled sketch not found in C:\Users\ADMINI~1\AppData\Local\arduino\sketches\1698...`，退出码 1。编辑器内容/样式均正常（#1/#2 修复生效）。

### #4 烧录失败：`This chip is ESP32-C3, not ESP32-S3. Wrong chip argument?` —— 🔧 已修（pkgout36，待复测）
- **来源**：**pkgout35 自带测试报告**（`LabCode-测试报告-20261007153709.txt`）——这套收集机制第一次实战就抓到真 bug。
- **现象**：插上 COM29（ESP32-C3）→ 点烧录 → 编译 **141988ms（142s）全过** → 烧录 13s 后失败：`esptool v5.3.0 … A fatal error occurred: This chip is ESP32-C3, not ESP32-S3. Wrong chip argument?` / `Failed uploading: uploading error: exit status 2`。工程 `jiqiren.ino`（732 行 / 25452 字节）本身没问题。
- **报告给出的三条硬证据**：
  1. `t=2112 target:change fqbn=esp32s3 port=COM29 boardName=""` —— 板卡**不是**本次识别出来的，是 `device.get()` 恢复的**上次选择**（S3）；
  2. `t=70013 board:autodetect fqbn="" name=""` —— 插入设备时 arduino-cli **认不出**型号（C3/S3/P4 原生 USB 共用 `303a:1001`）；
  3. `task:exit kind=upload code=1 outTail=…This chip is ESP32-C3, not ESP32-S3…` —— 硬件是 **C3**，目标是 **S3**。
- **根因（两层）**：
  - **表层**：目标板卡错了，且没有任何自动纠正（`esptool` 早就明说了该烧什么芯片）。
  - **底层**：**根本认不出板卡**。CLI 认不出 → 界面静默沿用历史板卡 → 白等一次 142s 全量编译 → 最后一步才被打回。（本项目红线早就写明「共用 VID:PID 时不得硬猜」，但这里缺的是「认不出时补一次实测」。）
- **修复（本次，两条并行会话 + 我各出一半）**：
  1. **烧录期自动纠正**（并行会话写入，我审过 diff 并纳入构建）：`build-diagnostics.parseChipMismatch` 识别 esptool 原话 → 主进程 `notifyChipMismatch` 广播 → 界面自动把板卡改成实测芯片并持久化，提示「请再点一次烧录」；gRPC / CLI 两条分支都调。
  2. **插板期补实测**（我新增）：CLI 认不出时用 **esptool `chip_id`** 直读芯片（`toolchain.probeChipId` + `findEsptool` + `parseChipIdFromOutput`），从 `Chip is ESP32-C3 (revision v0.4)` 取型号 → 映射 boardRegistry 的 fqbn → 自动选中正确板卡。**把 142 秒的错编译提前到插板那 1 秒解决**。
  3. **认不出时把话说出来**（我新增）：界面不再静默沿用，输出面板明写「没能认出型号（C3/S3/P4 同一个 USB ID），目标板卡仍是上次选的 XXX，请到硬件目标面板改」。
- **诚实标注**：`probeChipId` 依赖 arduino-cli 自带的 esptool（`Arduino15\packages\esp32\hardware\esp32\<ver>\tools\esptool_py\<ver>\esptool.exe`）；找不到 / 端口被串口监视器占用 / 超时 → 一律返回 null 并降级，**不影响任何既有功能**。真机上「插板能否自动纠正」**待复测**（报告里 `board:autodetect` 会新增 `probed` 字段，一眼能看出读到没读到）。
- **验证**：tsc 双过 + 自检全绿（build-diagnostics 65 / diag-log 25 / **chip-probe 9（新）** / board-registry 33 / hardware-intel 43）+ `scan-ipc-handlers` 0 命中 + `scan-ui-crash` 无风险 + 包内复核（`notifyChipMismatch` 与 `chip_id` 均在产物内）。
- **复测建议**：拔掉板子再插上（触发热插拔自动识别）→ 看输出面板是「检测到开发板：COM29 · ESP32-C3」还是「未识别到板卡型号」；后者说明 esptool 探测没生效，把新报告发我。

## 💡 功能介绍：悬停即显示（用户需求，2026-10-07，pkgout34）

**需求原话**：「用户点击某个功能可以做一个简单介绍吗」→ 用户选定形式 = **悬停即显示**；覆盖范围 = **硬链路（编译/烧录/串口/板卡）+ AI 助手面板 + 调试面板 + 项目与编辑器**。

**实现（为什么不包 Tooltip 组件）**：
- 新增全局单例 `FeatureHintLayer`（`src/renderer/src/components/FeatureHintLayer.tsx`）：`document` 上做**事件委托**，任何元素只要挂 `data-hint-title/desc/tip` 就出卡片，用 `createPortal` 挂到 `body`。
  → 组件里不写 hover 状态、**不包一层容器**，工具栏/图标带的 flex 紧密排布一点没动。
- 文案集中放 `src/renderer/src/featureHints.ts`（14 条），组件里只写 `{...hint('compile')}`。
- 三个防烦人细节：**延迟 420ms** 才显示（扫过一排按钮不会连闪）、卡片 `pointer-events:none`（永不拦点击）、按下去 / Esc / 滚动 / 失焦立即收。
- 定位：`useLayoutEffect` 量真实高度后决定放下方还是翻到上方，并夹在视口内（顶栏按钮也不会顶出屏幕）。

## 📦 本轮打包受阻记录（沙箱环境，非代码问题）

> ⚠ **2026-10-07 晚间更正：本段结论已被推翻。** 真实根因不是 asar 文件锁，而是旧打包配置 `files` 非白名单导致历史 `pkgout*/dist` 嵌套进 app（GB 级包 → NSIS EBUSY）。用 `builder.full.config.json`（白名单 + asar:false + npmRebuild:false）+ 全新输出目录已成功出包（pkgout30）。详见「方式 B」与错误记录 #1。以下原文留档。
- **现象**：electron-builder 打 NSIS 反复 `EBUSY: resource busy or locked, unlink '…\win-unpacked\resources\app.asar'`。
- **尝试过的 4 种办法全部撞同一文件锁**：① 全新输出目录 pkgout12；② 清空 `NODE_OPTIONS` 绕过 safe-delete shim；③ 再换全新 pkgout13；④ `--config.asar=false` 关归档 → 仍 EBUSY。
- **判定**：本机对**刚生成的 148MB app.asar 有文件锁**（Windows 杀软实时扫描大文件的典型症状；本机历史上 arduino-cli、git.exe 也反复 EBUSY，同源）。**不是 codelab 代码或 electron-builder 配置问题**，换环境（用户自己终端 / 无杀软）即可正常出包。
- **附带坑**：本机还有 `pkgout12/13/14` 三个失败残留目录（含锁住的 app.asar），删除会触发 safe-delete 护栏报错；它们已被 .gitignore 忽略，不污染仓库，重启后可手动清理。
- **替代交付**：用 `start-labcode.bat` 跑 `out/` 真实产物做真机测试（见上"方式 A"）。

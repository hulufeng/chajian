## 二、LabCode 实测数据（本次新测，打包版）

### 2.1 打包缺陷发现与修复（本次）
- **缺陷 ②：llama 本地引擎未入包**——打包版 `resources/llama` 缺失 → AI 发送后无回复。
  修复：package.json extraResources 新增 `{from:"resources/llama",to:"llama"}`（86MB 引擎：llama-server.exe + ggml 全套）→ 重新打包 155.9MB → 启动后 `llama-server` 进程在跑、`/health` 返回 `{"status":"ok"}`、3B 模型加载 2038MB。
- 修复前 q1"自我介绍"返回欢迎语（无真实生成）；修复后基础问答正常（见下）。

### 2.2 基础问答（q1："用一句话介绍你自己"）
- **500ms 内返回真实模型回复**："我是 LabCode AI 智能体，专注于帮助用户编写代码、执行命令、搜索网络、管理项目。"
- 结论：基础问答链路（发送→llama-server→生成→渲染）打包版可用，延迟 0.5–1s。

### 2.3 工具调用场景（q2："请读取当前打开的文件内容，并告诉我它实现什么功能"）
- **0–20s**：无回复、无 busy、无 worklog（模型生成长文本中，UI 无进行中状态）
- **40s**：回复"好的，请告诉我你希望读取哪个文件的内容？"
- **结论：本地 3B 模型没有调用 read_file 工具**——即便当前文件已在编辑器中打开，模型仍反问文件名。这是与 TrieCode 的核心差距（模型 Function Calling 能力弱 + 上下文未注入"当前打开文件"）。
- 附加观察：40s 生成本身说明 3B 处理复杂请求极慢；期间 UI 无"思考中/工作中"可视化，用户体验差。

### 2.4 知识库问答（q3：ESP32 GPIO 注意事项）
- 首次测试误判未回复，实际为脚本误判；教学知识库问答链路在源码版已验证全绿（handoff #57–#59，20 问实测）。打包版知识库目录已入包（resources/knowledge）。

## 三、TrieCode 实测数据（复用 docs/triecode-实机操作实测报告.md §2.4）

- **AI 对话（Agent 全链路）成功**：Agent 工作 16s，UI 显示"▶ 已工作 16s / 思考 · 1 个工具"——实际调用了 1 个工具（读文件），拿到代码后回答："TestBlink.ino 是一个空的 Arduino 框架文件，setup() 和 loop() 函数体均为空白，尚未写入任何实际逻辑。"（正确）
- **积分计量条**："输入 23.6k · 输出 58 · 消耗 1.68 积分"——token→积分换算对用户透明，商业化卖点级设计。
- 模型：MiniMax M2.7（云端）；execPath=account（账号计费）。

## 四、豆包 Agent 能力（公开资料）

- **工作任务模式（Agent）**：可在授权范围内处理本机文件/文件夹/应用/网页；调用 Skills（技能）、连接器（飞书办公/日历/消息）、定时任务；产出 Word/Excel/PPT/PDF/HTML 等文件产物。（豆包权威数据库：工作任务介绍/FAQ/核心能力）
- **专业版实测（36氪，2026-06）**：Agent 自主拆解任务，调用本地电脑、浏览器、飞书办公套件等工具，持续执行产出交付物；豆包 2.1 Pro 连续运行近 18 小时完成芯片 RTL 测试 Demo——长时间自主运行能力代表当前最强档。
- **平台能力（火山方舟）**：豆包大模型支持 Function Calling、内置工具（联网/图像/私域知识库）、MCP 工具扩展（volcengine.com/docs/82379/1827538）。
- **记忆**：长期记忆画像，越用越懂用户。

## 五、LabCode 商业化差距与改进建议

### 差距清单（按严重度）
1. **工具调用缺失（最关键）**：本地 3B 无法可靠触发 read_file/edit_file 等工具 → AI 只能"说"不能"做"，与 TrieCode"思考+1 工具"的体验差一个量级。用户已多次反馈"输出跟 triecode 不一样"。
2. **无工作状态可视化**：模型生成 40s 期间 UI 无"思考中/工作中"提示（TrieCode 有 16s 计时 + 工具计数）。
3. **无 token/积分计量**：TrieCode 显示输入/输出/积分，商业化信任感设计。
4. **工具调用提示不充分**：q2 场景模型反问文件名——说明系统提示词/上下文未注入"当前打开文件"路径，模型不知道有现成文件可读。

### 改进建议（按优先级）
1. **P0：提示词注入当前文件上下文**——发送请求时把当前打开的编辑器文件路径+内容片段注入系统提示词（或提供 @file 引用提示），模型无需工具调用也能"读文件"。已有提示"输入 @ 引用当前打开的文件"，但用户直接提问时未自动注入。
2. **P0：工具调用可靠性优化**——3B 模型对 read_file 等简单工具可走"强制工具路径"（检测到"读取/打开/查看文件"意图时，不经模型决策直接执行 read_file 并把内容注入回复），绕过模型工具决策能力短板（确定性工具路由）。
3. **P1：工作状态可视化**——生成期间显示"思考中/工作中"动画（TrieCode 式计时），UI 已在消息区可扩展。
4. **P1：token 计量条**——本地模型可显示生成 tokens/耗时/速度，为未来云端付费功能打底（TrieCode 式）。
5. **P2：云端模型接入**——用户已配 bluebubai.work 网关（5 内置模型待配 Key）；云端模型可解决工具调用与质量差距，与本地模型并存（本地=离线教学，云端=高级 Agent）。

## 六、结论

- **定位差异**：LabCode 本地 3B = "离线教学问答"（快、隐私、免费）；TrieCode/豆包 = "云端 Agent"（能动手、质量高、要联网/付费）。两者不是同一赛道，LabCode 的差异化是**离线+真实烧录闭环**。
- **商业化路径**：① 本地模型守住"离线教学"基本盘（P0 确定性工具路由补"读文件"体验）；② 云端模型（网关已就绪）提供高级 Agent 能力作为付费点；③ 补齐工作状态/计量 UI 建立信任感。
- **本次实测产出**：修复打包缺陷 ②（llama 入包），基础问答链路打通；工具调用差距量化（40s 反问 vs TrieCode 16s 工具调用），改进方向明确。
